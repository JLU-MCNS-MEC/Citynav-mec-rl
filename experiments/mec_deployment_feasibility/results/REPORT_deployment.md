# 阶段 2：真实 CityNav 地图 MEC 部署数量分析报告

生成时间: 2026-11-05
方法: 每张城市地图在**可通行区**（0.1m 高程 TIF 的 1m 有效掩码，`pipeline.py MapRaster`）
规则网格**均匀部署**（用户指示：无历史记录则均匀部署）；任务集合 = Train 22,002 +
Val-Seen 2,498 + Val-Unseen 2,826 = **27,326 个任务起点**，覆盖 28 张地图。
覆盖半径 500m、通信模型 = mec-v8.2 `latency_model.a2g_channel`（LOS 概率路径损耗 +
Shannon，载频 2GHz/GBS 10m/UAV 80m/带宽 5MHz/功率 0.1W），payload = 真实
CityNav 视觉 token 49×2048×16 bit = 1.6 Mbit（2026-11-05 审计统一口径）。

## 结论与建议

1. **推荐 K=10 并固定**：10 个 MEC 即可达到 100% 覆盖与 100% 任务可达，
   任务点平均 8 个可用 MEC（最少 8）、负载 σ 2.8；通信 P95 为 35.9ms。
   （注：审计修正后统一使用真实 CityNav 2048 维 token 口径；覆盖充分性
   与通信优化请见 AUDIT_2026-11-05.md 审计项 6 的区分。）
2. 部署位置已存 `mec_positions_k10.json`（28 张地图 × 10 个坐标，均匀部署，
   规则网格 + 有效区过滤）。
3. **注意**：v8.2 的 120m 最小间距在真实小尺度街区地图上无法处处满足
   （K=10 时 13/28 张地图需要放宽间距；K≥12 时全部 28 张需放宽）——真实地图
   可通行区碎片化程度远高于合成环境，此为真实/合成环境差异，已在结果中
   逐图记录 `spacing_relaxed` 标志。
4. **通信时延口径（2026-11-05 审计修正）**：payload 为真实 CityNav 视觉 token
   49×2048×16bit = 1.6 Mbit（此前本报告误用 v8.2 ViT 的 384 维，低估 5.33 倍）。
   统一口径后通信 P95 = 51.7/42.1/35.9/36.3/32.2/29.3 ms（K=5/8/10/12/15/20），
   与阶段 5 E2E 报告一致（K=10 均为 35.9ms）。
