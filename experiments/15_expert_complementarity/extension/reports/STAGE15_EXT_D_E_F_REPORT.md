## F · 能耗模型与 100 任务统计

### F1. 动作时间审计

| 动作 | 几何 | 时间假设 | 状态 |
|---|---|---|---|
| Forward | 5.0 m | 1.0 m/s → **5.0 s** | 仿真假设（待校准） |
| TurnLeft/Right | 30° | 30°/s → **1.0 s** | 仿真假设（待校准） |
| Stop | — | 终止 | — |
| 编码 | — | 5.450 ms | Stage 12 |
| 通信 | 依距离 | 24–126 ms | Stage 12 |
| 推理 | 依模型 | 0.495–19.972 ms | P0 实测 |

> CityNav 原始代码只定义离散位移/角度，**没有速度/角速度**；以上为显式仿真假设，
> 不得声称为实测参数。

### F2. 推进功率（Zeng et al., IEEE TWC 2019）

```
P(v) = P0(1 + 3v²/Utip²) + Pi·sqrt(1 + v⁴/(4v0⁴)) + 0.5·d0·ρ·s·A·v³
P_hover = P0 + Pi = 168.49 W
```

| 参数 | 值 | 来源 |
|---|---:|---|
| P0 | 79.86 W | Zeng 2019 |
| Pi | 88.63 W | Zeng 2019 |
| Utip | 120 m/s | Zeng 2019 |
| v0 | 4.03 m/s | Zeng 2019 |
| d0 | 0.6 | Zeng 2019 |
| ρ | 1.225 kg/m³ | 标准大气 |
| s | 0.05 | Zeng 2019 |
| A | 0.503 m² | Zeng 2019 |
| P_enc | 15 W | **仿真假设** |
| P_tx | 0.1 W | Stage 12 |
| P_aux | 5 W | **仿真假设** |
| 电池 | 100 Wh | **仿真假设** |

### F3. 每步能耗构成

```
E_step = E_move + E_wait + E_aux
E_move = P(v) × t_move               (Forward/Turn)
E_wait = (P_hover + P_enc + P_tx) × (t_enc + t_comm + t_infer)
E_aux  = P_aux × (t_move + t_wait)
```

无重复计算：移动时用推进功率；编码/通信/推理等待期间用悬停功率 + 额外负载。

### F4. 100 任务统计（Min-Latency 基线）— 已修正

> **BUG 修正（2026-11-25）**：前一版统计把 MEC 节点索引（0–9）当作导航动作（0–3）
> 传给 `step_energy()`，导致节点索引 ≥4 的步被算成"原地不动"，能耗被低估约 11 倍
> （75 J/步 → 832 J/步）。旧 CSV 保留为 `energy_stats_100_BUGGY_node_as_action.csv`。
> 下表为修正后结果。

| 指标 | 值 |
|---|---:|
| 任务数 / 成功数 | 100 / **44** |
| 平均 Episode 能耗 | **47,476 J（13.19 Wh）** |
| P50 | 40,571 J（11.27 Wh） |
| P90 | 81,490 J（22.64 Wh） |
| P95 | 102,121 J（28.37 Wh） |
| 成功任务平均 | **36,093 J** |
| 失败任务平均 | **56,420 J** |
| 能耗分量占比 | 移动 **96.3%**、等待 0.85%、辅助 2.88% |
| 电池占用（100 Wh） | 平均 **13.2%**，P95 **28.4%** |
| corr(能耗, 步数) / corr(能耗, 累计 E2E) | 0.997 / 0.974 |

**修正后的关键观察**：

1. 能耗几乎完全由**移动时间**决定（96.3%），而移动时间来自仿真假设 v = 1 m/s；
   若把前飞速度改为 5 m/s，单步前飞能耗会从 ~840 J 降到 ~180 J（约 4.7 倍）。
   **速度假设是能耗模型里最敏感的参数，必须在写进论文前校准。**
2. **失败任务的能耗显著高于成功任务**（56.4 vs 36.1 kJ）。这说明在"单任务硬预算"
   下，能耗约束会倾向于**更早失败**——与 SR 约束方向冲突。设计双约束 CMDP 时
   不能只加一个"最小化能耗"的项，否则会重演 Stage 16 原奖励 A 的老问题。
3. 100 Wh、单任务预算下 P95 仅占 28.4%，约束在多数任务上不构成限制。
   更合理的做法是把预算按任务尺度归一（例如按 SPL 或按起终点距离），
   或用"每米能耗"这样的强度量，而不是绝对焦耳。

## 当前结论与建议

1. **D1–D3 数据链路已打通**，但 100 状态规模不足以支撑画像评估；
2. **E 画像尚无可信结论**（Dev 无敏感状态、AUC 无法计算）；
3. **F 能耗模型已建立**，参数来源清晰，100 任务统计已完成（并修正了动作索引 bug）；
4. **能耗 ≈ 移动时间 ≈ 1/v 假设**；失败任务能耗更高，说明能耗与 SR 存在冲突，
   预算需要按任务尺度归一；100 Wh 下 P95 仍只占 28%；
5. **下一步建议**：
   - 扩展到 **1000 状态**（200 任务 × 5 快照）：快照 ~5 分钟，分支 ~86 分钟；
   - 按 Task ID 划分 160/40，保证 Dev 含正负样本；
   - 重新训练画像并评估敏感状态识别；
   - 在确认能耗参数（尤其电池容量与 v_forward/ω_turn）后再设计 SR/能耗约束。

**本轮未启动任何大规模 DRL 训练。**
